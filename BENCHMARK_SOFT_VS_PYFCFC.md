## Headline

* isotropic: `pyfcfc (CPU, SIMD)` forward takes 2.3x the cucount GPU pass (4.48 s versus 1.96 s).
* multipoles: `pyfcfc (CPU, SIMD)` forward takes 1.0x the cucount GPU pass (7.80 s versus 7.48 s).
* isotropic: `cucount (CPU, 32 threads)` forward takes 4.8x the cucount GPU pass (9.36 s versus 1.96 s).
* multipoles: `cucount (CPU, 32 threads)` forward takes 3.1x the cucount GPU pass (23.44 s versus 7.48 s).
* isotropic: the GPU pass is 4.8x faster than cucount on 32 CPU threads.
* multipoles: the GPU pass is 3.1x faster than cucount on 32 CPU threads.

## Caveats

* pyfcfc is CPU-only, so the GPU rows have no counterpart; the CPU rows are the honest like-for-like comparison.
* Both codes count autocorrelation pairs twice here (pyfcfc by convention, cucount because the catalogue is passed as two copies), so a single ordered-pair normalisation applies to all curves.  pyfcfc folds mu into [0, 1) while cucount keeps the sign: even multipoles are unaffected.
* cucount on the CPU goes through the numpy frontend: the jax frontend is CUDA-only, so a jax-to-jax comparison on the CPU is not available yet.
* Timings are wall clock around one call: they include the Python/pybind11 dispatch and the host/device copies, but not jax tracing or compilation, which are warmed up first.
* The kernels are compared at the same normalisation: pyfcfc renormalises per pair, and cucount runs `soft_norm='softmax'` (`--soft-norm`, its default) to match. cucount's own default is now `soft_norm='gaussian'`, which skips that second pass: keep the pinned mode when the point is to compare against the oracle, and pass `--soft-norm gaussian` when the point is to measure the default.
